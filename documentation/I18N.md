# Interface languages: how translations are handled (2026-11-05)

Question: is hand-writing a dictionary per language the right way? No. Hand dictionaries are the bottleneck; the page must know which languages it has and make adding one cheap.

## What I looked at
- Tooling (gh, 2026-11-05): Weblate (6,158 stars, pushed 2026-11-05), Tolgee (4,155, 2026-11-05), Lingui (5,934, 2026-11-03), i18next (8,663, 2026-11-04), Paraglide-js (794, 2026-11-04). Licences not read. All except Weblate/Tolgee assume a bundler; this site is static HTML with no build step.
- Browser built-in translation: MDN and Chrome docs list `Translator` and `LanguageDetector` as shipped in desktop Chrome (docs say 138, a Google post says 144), Edge 148, not in Firefox or Safari, model downloaded on demand. Sources disagree on the Chrome version; not Baseline.
- Workflow articles (vendor blogs, so weak evidence): the common pattern is machine draft, then targeted human review, with strings kept out of components.
- Our own test (this repo): the project's Opus-MT drafts for UI text. Czech "Zkus to teď" (informal), "A guest session starts by itself" became "Sezení hostů začíná samo od sebe" (guests' seating) in Czech and a nonsense line in Chinese, Hindi dropped half the sentence, Slovak "for speech to text" became "pre reč k SMS". Fine for a reviewer's first pass, not for publishing.

## What is implemented
1. English text is the key (gettext style): `ui/i18n/<code>.json`. No build step, no per-string ids to maintain.
2. `scripts/i18n_tool.py extract|missing|coverage|draft` scans every page and script (`t()`, `T()`, `N_()`) so missing strings are found, not remembered. Legal pages are excluded on purpose (one reviewed language until a lawyer checks).
3. Two machine sources, tracked per string in the catalog `_meta`:
   - `draft <code>`: local Opus-MT (batched, about 8 s per language). Rough, so listed in `raw_keys` and NOT shown: the page falls back to English unless `?drafts=1` (or `localStorage.i18nDrafts=1`) is set.
   - `translate <code>`: an LLM pass through NVIDIA NIM (`nemotron-3-ultra-550b`, key `NIM_3`, free tier, public interface text only) with a glossary of product terms, placeholder checks and a retry for missing keys. Listed in `draft_keys`: shown, and the picker labels the language "Machine draft" while under half of it is human-reviewed.
   A reviewer fixes a string and removes it from either list.
4. `scripts/ui_manifest.py` writes `ui/i18n/index.json` with coverage measured against the strings the pages really contain; a locale below 50% reviewed coverage is a preview and stays out of the picker. `test/i18n_dict_test.py` fails if a shipped locale covers under 75%.
5. Interface language and speech languages are separate: the first comes from catalogs, the second from the server (`ui/shared/caps.js`). Both use one picker. Language names come from `Intl.DisplayNames`, so a new code needs no name table.
6. Starting language: the link, then the last pair this browser used, then `navigator.languages`, then the first ready route. Nothing defaults to English.

## Current state (after the NIM pass)
| Locale | Shown | Human-accepted | Source |
|---|---|---|---|
| en | 100% | 100% | source text |
| sk, de | 99% | 81% | assistant-written home/live strings (owner accepted), 72 doc-page strings by NIM |
| cs, pl, uk, hu, es, fr, ro | 99% | 0% | NIM `nemotron-3-ultra-550b` (about 386 strings each, about 4 min per language), labelled "Machine draft" in the picker; the home footer shows "Improve this translation", which opens the feedback form prefilled with the language and page |
Ukrainian needed Cyrillic fonts (added: `ui/vendor/fonts/*-cyrillic.woff2`, one @font-face per weight, because a face is picked by weight before unicode-range). Counts use `Intl.PluralRules` with a `[few]`/`[many]` key convention (`tp()`), so "9 мов" and "8 маршрутів" are correct. Raw Opus-MT output for hi and zh was judged unusable and deleted; regenerate with `draft hi`.
Checks: `make i18n` (coverage + manifest freshness), `test/i18n_dict_test.py`, `test/ui_manifest_test.py`.

## Tools the owner pointed at (read 2026-11-05)
- `Mr-vero/AutoTranslate`: 9 stars, last push 2024-03-07, no licence. Runtime page translation through SeamlessM4T with an IndexedDB cache. Not adopted: every visitor's page text would go to an external model on each load, the repo is stale and unlicensed, and results are not reviewable. Idea kept: cache translations.
- `tzum3498/website-translation-tools`: 2 stars, a 2025 listicle of commercial services (Weglot, Smartling, Lokalise, Phrase). Not adopted: paid SaaS. Ideas kept: glossary, translation memory, an in-page way to correct a string.

## Better options, in order
1. LLM-assisted pass with a glossary and style guide instead of raw Opus-MT: much better UI tone, costs tokens (needs owner approval to spend) or an assistant session like the one that wrote sk/de.
2. A native reader per language, reviewing in a PR or in Weblate once there are two or more reviewers.
3. Optional "Translate with your browser" for locales without a catalog, via the `Translator` API where it exists (desktop Chrome/Edge). Not a primary path: model download, no Firefox/Safari, quality not under our control.
4. More Opus-MT models (de, pl, uk, hu, es) converted with `scripts/convert_models.py` to widen the draft source (downloads: ask first).
