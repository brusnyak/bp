## Best achievable product (the ceiling)

"Interpreter booth in a link." The host speaks once. Anyone opens the link (no account), picks their own language, and hears and reads the translation, in the host's voice where a voice exists. Gap today: no rooms/fan-out (one session per speaker), audio exists for only three target languages (sk, cs, en), cloning needs a GPU, concurrency unmeasured (claims.md #6). So the site must sell what runs (live translation, own machine) and show the booth as a roadmap, not a feature.

## Findings

### Cross-cutting
1. Three navigation systems at once: burger menu, top bar, left section rail. The rail lists 7 items and omits "Run it yourself" and "Measured performance" (both have ids `setup`, `measurements`, no rail item, no menu item).
2. Every section is `full-screen` (min-height 100vh) with a different tint (pink, cream, blue-grey, mint, grey). Result: 10,094 px on desktop and 15,947 px on a phone, big dead gaps, and a rainbow that breaks DESIGN.md "vars only". Screenshots: hero has ~190 px empty above and below the card; pipeline section has ~250 px empty below.
3. Same CTA "Try it now" four times, plus "Learn more" twice, one of which loops to the section above.
4. Text-first everywhere; nothing on the page responds to the visitor except the FAQ and the video thumbnail.

### 1. Language selection
- `ui/i18n/i18n.js`: `LANGS = { en, sk, de }`, hand-translated gettext dictionaries (354 keys each). Adding a language = translating 354 strings by hand. The switch is a native `<select>` showing "EN", tiny, no names, no search.
- It conflates two different things: interface language (UI strings) and speech languages (what the product translates). The live page has a third control for the same thing: fixed text "English → Slovak" plus Swap, and also a dropdown in each caption panel.
- Real speech coverage (`languages/packs`, `ct2_models`, `piper_models`): packs declared for sk, cs, de, pl, hi, zh, fr, ja. MT models installed for cs, sk, hi, zh, ja, fr, pl (to/from en). Piper voices installed only for en, cs, sk. So only en→sk, en→cs, sk→en can produce speech; the others are captions-only at best, and de has no MT model installed.
- Fix: (a) interface locale list generated from a manifest (`ui/i18n/locales.json`: code, native name via `Intl.DisplayNames`, direction, status), searchable sheet, native names, current one checked; (b) speech picker is a separate From / swap / To control with three honest tiers: Speech + captions, Captions only, Experimental; (c) draft new UI locales with the local Opus-MT models, flag "machine-translated" until a native reader checks; RTL ready (`dir`); (d) one source of truth for the pair, panels become labels.
- Interface languages to ship first (proposal, owner to pick): en, sk, cs, uk, de, pl, hu, fr, es. Note: uk/hu/es MT models are not installed, so a draft needs a download (asks first).

### 2. Hero

### Live speech

- Fix: one primary button "Start" (initialises implicitly, shows progress, falls back to Initialize on failure); sound check becomes a first-run sheet (skip-able, remembered); From / swap / To as the only language control; captions above settings once running; settings collapse into a sheet; voice and meeting options move to "Advanced".
- Multi-user: needs a backend room model (host token, listener tokens, per-listener target language, MT fan-out, TTS per language). `documentation/MULTI_USER_SERVER.md` exists but I did not read it. Spec first; do not put "rooms" on the home page until a pilot and a concurrency test exist.

## Apple design principles to apply (verify against developer.apple.com/design/human-interface-guidelines before building)
- Clarity / deference: content first, one accent colour (berry), fewer boxes.
- Sheets and menus for pickers (language), segmented control for the 2-3 way choices (tabs in Get started), single translucent top bar with `backdrop-filter`, no burger on desktop; a bottom tab-bar style sheet on phone.
- 44 px minimum touch targets, text that scales (clamp/rem), 4.5:1 contrast, visible focus, `prefers-reduced-motion` and `prefers-color-scheme` honoured.
- Motion explains cause and effect (the stepper, the caption replay), spring-ish easing, nothing decorative.

## Roast
- Weakest point: the page is a thesis report wearing a landing-page skin. The visitor is asked to read 5,000 words before touching anything, and the most honest content (limits) crowds out the one thing that persuades: hearing a translation.
- Cheapest failure: you ship 9 languages in the UI picker, a visitor picks Polish for speech, gets captions with no voice, and leaves. Smallest fix: tiers in the picker plus a disabled "no voice yet" state.
- Second: "multi-user" is on the wish list with no named listener group; building rooms before one pilot is the expensive way to learn nobody needs them.

# Revision 2 (owner: nothing hard-coded; the project knows what is available, loads it easily, picks the best)

## What the code already has (checked)
- `backend/registry.py`: engine registry. Each engine is a `Capability` (stage, factory, cheap `probe`, languages, devices, streaming, licence gate that fails closed). This is the right core.
- `languages/packs/*.json` + `scripts/language_packs.py`: a language pair is a data file; `resolve()` reports which assets exist; `bp language test` writes an eval record under `processed/language_eval/`. 13 packs declared.
- `backend/hardware_scan.py`: detects CPU/RAM/GPU and picks STT size, MT device, TTS engine.
- `GET /api/routes` (`backend/main.py:843`): the inventory of packs and their assets.

## The gap (checked)
1. The UI ignores all of it. `ui/live-speech/live.html:271-300` hard-codes 17 language `<option>`s and `:158-162` hard-codes 5 TTS engines. `live-script.js:959` calls `/api/routes` only as a yes/no gate at Initialize. Home i18n hard-codes `{en, sk, de}` (`ui/i18n/i18n.js`).
2. Nothing ranks. The registry answers "may this ship / is it installed", not "which is best here". `hardware_scan` picks a stack per machine, but language/engine choice per pair is by hand in the pack.
3. Nothing offers what could be installed. Real catalogue sizes I fetched: Piper `voices.json` has 178 voices across 53 language families (so most of the world has a voice available to install); Hugging Face lists about 470 `opus-mt-en-*` models (search hit, includes multi-target and duplicates, not a verified pair count). The shipped set is 3 spoken targets.
4. Two controls hold the same fact on live (pair text + per-panel dropdowns), and the engine `<select>` can disagree with the pack.

## Target: one discovery contract, everything renders from it
`GET /api/capabilities` (new, read-only, no model loading) returns, merged from what already exists:
- `engines`: `registry.catalog()` (name, stage, available, reason, licence, devices, streaming).
- `routes`: one row per pair from packs + `resolve()`: `{pair, tier, stages:{stt,mt,tts}, evidence, ready, missing:[...]}` with `tier` = `speech` (STT+MT+TTS present), `captions` (no voice), `installable` (a catalogue source exists, not downloaded), `experimental` (no evaluation record).
- `languages`: derived set of codes from the routes (source side and target side), each with native name and English name from `Intl.DisplayNames` on the client. No language list in HTML or JS.
- `hardware`: `scan_hardware()` summary.
- `recommended`: per pair, an ordered list of engine choices with a reason string. Policy (deterministic, unit-tested): licence ok, then installed, then eval evidence (WER/latency record) for this pair, then hardware fit, then streaming support. The UI shows "Auto (recommended)" and the reason; "Choose engine" is an Advanced override.
- `installable`: catalogue entries not installed (Piper voice ids with size and licence, Opus-MT ids), each flagged `needs_operator` because downloads need approval and a licence note.

Adding a language or engine = drop a pack JSON / register a `Capability`. The UI, the picker, the ranking and the home page counters pick it up with no UI edit. Same rule for the interface locale: `ui/i18n/<code>.json` + a generated `ui/i18n/index.json` (code, native name, direction, coverage %, `machine_draft` flag); `i18n.js` reads the index. A `bp i18n draft <code>` script can pre-fill a locale with the local Opus-MT, flagged until a native reader signs it off.

Pivot: when no direct MT exists for X to Y, route X to EN to Y (already specified in `ARCHITECTURE_V2.md` section 6, about +0.1 s). The capabilities endpoint should mark such pairs `via: en` so the picker can show them honestly.

## Research on design (what I read, what it says, what I will use)
Read in full: `emilkowalski/skills` `apple-design/SKILL.md` (23 KB) and the `ui-cheatsheet.md`. Headings and descriptions only: `mobile-native`, `break-ui`, `prototype`, `pick-ui-library`, `emil-design-eng`. Not read: the other 11 skills in that repo (animate, choreograph, review-animations, improve-animations, write-swift and others). Repo facts from `gh`: MIT, 53,673 stars, last push 2026-11-04, 17 skills. Other repos found by search (not opened): raintree-technology/apple-hig-skills (14 HIG skills; its README says the HIG text is Apple IP; licence listing inconsistent), axiaoge2/apple-hig-designer (MIT), nutshellengineering/apple-design-skill (Apache-2.0, unofficial HIG mirror). Locally already present: `impeccable`, `ui-ux-pro-max-skill` in `~/Developer/refs`.
Caveat: `apple-design` is distilled from WWDC talks (fluid interfaces, motion, materials, type, the eight principles); it is not the HIG component rules (sheets, segmented controls, sidebars). For component rules use developer.apple.com directly (not fetched yet) or the raintree skills.

Applied to this project:
- Response on pointer-down, `transform: scale(0.97)` on `:active`, 44 px targets, ease-out under 300 ms, popovers anchored to their trigger (`transform-origin`). Affects the language sheet, Start button, tabs.
- Interruptible, critically damped (damping 1.0) motion; bounce only for flick-driven things. I will not add springs to a marketing page: Emil's own `remove-animations` and the HIG "Purpose / Simplicity" say restraint. One authored motion moment (hero caption replay) and the pipeline stepper are enough.
- Translucent top bar with `backdrop-filter`, with `prefers-reduced-motion`, `prefers-reduced-transparency` and `prefers-contrast` fallbacks. No stacked light-on-light surfaces.
- Type: size-specific tracking (headings about -0.02em, body 0), tight leading on large text, `rem` spacing so text size settings scale the layout. DESIGN.md keeps Playfair/Montserrat; the skill says prefer the system font, so this is a deliberate exception to record, not a silent override.
- `mobile-native`: 100vh bug (the hero is `full-screen`), inputs under 16 px zoom iOS, tap highlight, safe-area insets, sticky hover. Directly relevant to the 390 px problems.
- `break-ui`: run worst-case data through the language picker (long native names, Arabic/Hebrew RTL, CJK, 60+ entries, zero installed routes, one route). This is the right test for a data-driven list.
- `prototype`: build 2-3 variants of the hero and the picker behind a switcher and let the owner choose, which also satisfies DESIGN.md's "owner decides" rule.
- Language picker UX (web search, UX blogs and the US digital.gov design system): native name first with the English name beside it, search for 30+ items accepting native and Latin input, no flags, regional variants labelled, alphabetical by native name, one independent button.
- Listener journey (Wordly's public pages, vendor-authored so treat as indicative): scan a QR or open a link, pick a language, optionally enter a name, join; no account or install; one QR/URL per room; audio, captions or both. This is the model for "guests gracefully".

## Roast of this plan
- Weakest point: ranking needs evidence, and only a few pairs have an eval record. Until more exist, "best" collapses to "installed and licence-ok", which is honest but modest. Smallest fix: run `bp language test` on every installed pair so the ranker has data, and show "not evaluated" in the UI.
- Cheapest failure: an "installable" list of 178 Piper voices invites clicks that nothing can satisfy. Smallest fix: no install button until a gated, owner-approved installer exists; show it as "available to the operator".
- A UI that reflects every installed model can show a language whose voice is bad. Quality is not in the manifest; a native-listener grade is, and it should gate the `speech` tier label.
